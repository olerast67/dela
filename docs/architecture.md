# Dela: архитектура

Документ фиксирует принятые решения. Меняется вместе с кодом: если код расходится с документом, правится одно из двух в том же коммите.

## Принципы

1. **Local-first.** Каждое устройство хранит полную копию данных в SQLite. Интерфейс читает и пишет только локальную базу.
2. **Сервер не видит содержимого.** Шифрование включено всегда, выключить его нельзя. Сервер хранит, упорядочивает и раздаёт зашифрованные операции и проверяет права.
3. **Слияние на клиентах.** Все клиенты применяют одни и те же детерминированные правила и приходят к одному состоянию.
4. **Ядро одно.** Модель, синхронизация, шифрование, разбор фраз, повторы и фильтры живут в `packages/core` и работают на всех платформах.

## Репозиторий

```
packages/core      ядро: TypeScript без зависимостей от платформы
apps/server        сервер: Node.js 24, node:sqlite, Hono
apps/web           веб-клиент: React, Vite, IndexedDB, PWA
apps/desktop       Tauri 2: встроенный веб-клиент, трей, глобальная клавиша, уведомления
apps/mobile        Capacitor: встроенный веб-клиент, напоминания через расписание Android
```

Один корневой `package.json` без npm workspaces: workspaces требуют символических ссылок, а репозиторий должен работать и на дисках без них (exFAT). Ядро подключается через subpath import `#core` из корневого `package.json`. Его понимают Node.js, TypeScript и Vite.

TypeScript пишется в стиле, который Node.js запускает без сборки (type stripping): импорты с расширением `.ts`, без `enum`, `namespace` и свойств в параметрах конструктора (`erasableSyntaxOnly`). Сборка нужна только веб- и мобильному клиенту, их собирают Vite и Metro.

## Операция

Единица изменения: новое значение одного поля одной записи.

```ts
interface Op {
  table: string   // "task", "project", ...
  record: string  // UUIDv7, создаётся на клиенте
  field: string   // "title", "due", ...
  value: Json
  hlc: string     // метка гибридных часов
}
```

**Слияние.** Для каждой ячейки `(table, record, field)` побеждает операция с большей меткой `hlc`. Метки сравниваются как строки.

**Метка HLC**: `WWWWWWWWWWWWWWW-CCCC-NNNNNNNNNNNNNNNN`
- `W`: физическое время в мс, 15 десятичных цифр;
- `C`: счётчик в base36, 4 знака (до 1 679 615 операций в одну миллисекунду);
- `N`: id устройства, 16 hex-символов.

Формат фиксированной ширины, поэтому строковое сравнение совпадает с логическим. Метки двух разных устройств никогда не равны.

**Расхождение часов.** Сервер отклоняет операции с временем больше своего на 60 с и сообщает своё время; клиент хранит поправку и передаёт часам `now = Date.now() + offset`. Клиент при получении чужих меток не отклоняет их, иначе синхронизация встанет.

**Порядок в списках**: дробные ключи (base62, алгоритм Greenspan/rocicorp). Перестановка задачи меняет одно поле. При одинаковых ключах (две вставки в одно место офлайн) порядок решает `record`.

## Состояние на устройстве

- Хранилище на устройстве (в браузере IndexedDB, на телефоне нативная SQLite) хранит только ячейки, очередь исходящих операций и курсоры. Схемы таблиц задач в нём нет. IndexedDB выбрана вместо SQLite WASM: ей не нужны заголовки изоляции (COOP/COEP) и она работает в нескольких вкладках сразу.
- В браузере ключи аккаунта и пространства хранятся зашифрованными неизвлекаемым ключом AES-GCM (WebCrypto). Синхронизирует одна вкладка (Web Lock), остальные получают изменения через BroadcastChannel.
- При запуске ячейки загружаются в `Doc` (ядро), он держит разобранный снимок в памяти. Запросы «Сегодня», «Предстоящие», проекты, поиск и фильтры выполняет ядро, одинаково на всех платформах. 50 тысяч задач занимают десятки мегабайт.
- Метки задачи хранятся отдельными ячейками `label:<id>` со значением `true`/`false`, поэтому метки, добавленные на разных устройствах офлайн, складываются.
- «Входящие» имеют id, равный id пространства: два устройства, создавшие их офлайн, создают одну запись.
- Подзадача наследует проект и раздел от верхнего предка. Удалённый предок или проект прячет потомков, восстановление подзадачи восстанавливает предков.
- Циклы в дереве (A в B и B в A офлайн) разрываются при чтении: игнорируется перемещение с самой старой меткой поля `parent`.

## Нативные оболочки

- Компьютер (Tauri 2) и телефон (Capacitor) запускают тот же собранный веб-клиент из `apps/web/dist`, встроенный в приложение. Адрес сервера пользователь вводит при первом входе; API сервера открыт для запросов с любого источника (CORS), потому что вход идёт по токену в заголовке и cookie нет.
- React Native я отложил: отдельный интерфейс для телефона удваивает работу, а Capacitor даёт нативные модули там, где они нужны. Если производительность списков на телефоне окажется недостаточной, интерфейс телефона можно переписать, ядро останется общим.
- Телефон ставит напоминания в расписание Android (ближайшие 60 на неделю вперёд): они приходят при закрытом приложении и без связи с сервером.
- Компьютер прячет окно в трей при закрытии, напоминания показывает плагин уведомлений Tauri. `Ctrl+Shift+Space` открывает быстрый ввод из любой программы.
- Ключ подписи Android хранится вне репозитория (`~/dev/keys/dela-release.properties` или путь из `DELA_SIGNING`).

## Общие проекты

- Общий проект живёт в отдельном пространстве со своим ключом. Id проекта равен id пространства, своих «Входящих» там нет.
- Сделать проект общим: создать пространство (ключ обёрнут мастер-ключом владельца), скопировать в него проект, разделы и задачи (они перешифровываются ключом пространства), удалить их в личном пространстве.
- Приглашение: владелец получает открытый ключ участника по адресу почты (`GET /api/users/public-key`) и шифрует ключ пространства для него `crypto_box` своим секретным ключом (формат «DB1», привязка к пространству и версии ключа). Интерфейс показывает отпечаток ключа участника для сверки по другому каналу, и этот ключ закрепляется в личном пространстве владельца (таблица `pin`, зашифрована и синхронизируется между его устройствами).
- Участник при первом получении ключа закрепляет открытый ключ владельца. Ключ проекта от другого отправителя не принимается, участник видит отпечаток и может доверять новому владельцу вручную. Так сервер не может выдать свой ключ проекта под видом владельца. Анонимно запечатанный ключ (приглашения до 0.4.1) принимается только в первой версии ключа.
- При смене ключа владелец сверяет список участников с сервера с закреплёнными ключами: участник с другим ключом или без закрепления останавливает смену до подтверждения отпечатков.
- Клиент держит `Workspace`: личный и общие документы как одно целое. «Сегодня», поиск и фильтры собираются по всем, правки уходят в пространство записи, перенос задачи между пространствами — копия и удаление.
- Метки личные и в общие проекты не переносятся.
- Исключённый участник теряет доступ к серверу. Владелец сразу меняет ключ пространства (`POST /api/spaces/:id/rotate`): всё содержимое шифруется новым ключом заново, каждый оставшийся участник получает новый ключ, запечатанный своим открытым ключом, старые конверты удаляются в той же транзакции, `key_version` растёт. Сервер принимает смену, только если журнал не вырос с `baseSeq`, иначе ответ `stale`, и владелец догружает правки и повторяет. Отправка со старой версией ключа получает `409 key_rotated`; клиент берёт новый ключ и отправляет ту же очередь заново (очередь хранит операции открытыми и шифрует их при отправке). Исключённый сохраняет то, что уже видел, но изменений после смены ключа прочитать не может.

## Комментарии и файлы

- Комментарий это запись таблицы `comment` в пространстве задачи: задача, текст, автор (id пользователя), время, файл. Как и всё остальное, она шифруется ключом пространства.
- Файл шифруется на устройстве XChaCha20-Poly1305 новым случайным ключом; AAD `dela/file/v1`, пространство и id файла. Сервер хранит шифротекст в таблице `files` (до 7 МиБ на файл, предел на пространство `DELA_MAX_FILE_MB_PER_SPACE`), ключ файла лежит только в зашифрованной записи комментария.
- Удаление комментария затирает текст и файл; клиент удаляет и шифротекст файла на сервере. Удаление задачи навсегда удаляет и файлы её комментариев. Файлы отдаются только участникам пространства, поэтому убранный участник не скачает файл, даже если сохранил его ключ.
- Комментарий подписан автором. Ключ подписи Ed25519 выводится из мастер-ключа (`crypto_kdf` id=1 «dela_sig»), открытая часть хранится на сервере (`users.sign_key`) и отдаётся в списке участников. Подпись покрывает пространство, id комментария, задачу, автора, время, текст и файл. Ключ подписи участника закрепляется при первом появлении в личном пространстве (`pin` с id `sig:<userId>`). Заменить уже стоящий на сервере ключ можно только с паролем.
- Исполнитель: поле `assignee` задачи (id участника) в общих проектах.

## Синхронизация

Сервер хранит для каждого пространства журнал конвертов:

```
seq      порядковый номер, растёт
slot     непрозрачный id ячейки (см. «Шифрование»)
hlc      метка операции, открыта
payload  шифротекст
```

- **Отправка.** Клиент шлёт пачку конвертов. Если для слота уже лежит конверт с меткой не меньше, новый отбрасывается. Иначе старый удаляется, новый записывается с новым `seq`. Повторная отправка той же операции ничего не меняет.
- **Получение.** Клиент запрашивает конверты с `seq` больше своего курсора, страницами.
- **Сжатие.** В журнале остаётся только последний конверт каждого слота. Клиент, который пропустил промежуточные версии, получит последнюю: для LWW этого достаточно.
- **Сигнал.** По WebSocket сервер шлёт только «в пространстве N есть новое».
- **История активности** будет храниться отдельно и в зашифрованном виде (фаза 2).

Эталонная реализация правил сервера: `packages/core/src/relay.ts`. Сервер на SQLite обязан проходить те же тесты.

## Шифрование

Примитивы libsodium: Argon2id, XChaCha20-Poly1305, X25519 (`crypto_box_seal`), BLAKE2b с ключом, `crypto_kdf`.

### Ключи

```
пароль ──Argon2id(соль)──► 64 байта
                            ├─ 32: секрет входа → серверу (сервер хранит его хеш)
                            └─ 32: ключ обёртки (KEK) → расшифровывает мастер-ключ

мастер-ключ (случайный, 32 байта)
  ├─ обёрнут KEK и ключом восстановления, хранится на сервере
  ├─ шифрует секретный ключ X25519 пользователя
  └─ шифрует ключи личных пространств

ключ пространства (случайный, 32 байта)
  ├─ crypto_kdf id=1 "dela_enc": ключ шифрования операций
  ├─ crypto_kdf id=2 "dela_slt": ключ слотов
  └─ для общего пространства запечатан открытым ключом каждого участника
```

- Пароль на сервер не уходит. Из ключа входа сервер не может получить KEK.
- Соль выдаётся по e-mail до входа. Для несуществующего адреса сервер отвечает детерминированной поддельной солью (HMAC от секрета сервера), чтобы по ответу нельзя было проверить, зарегистрирован ли адрес.
- Смена пароля перешифровывает только мастер-ключ.
- Ключ восстановления: 32 случайных байта, показывается при регистрации. Без пароля и без него данные не восстановить.
- Открытые ключи участников проверяются по отпечатку (как safety number в Signal), до проверки действует доверие при первом использовании.

### Конверт операции

```
slot    = BLAKE2b-128(ключ слотов, JSON [table, record, field]), hex
payload = nonce(24) ‖ XChaCha20-Poly1305(
            ключ шифрования,
            pad64(JSON {t, r, f, v}),
            AAD = space ‖ slot ‖ hlc)
```

- Сервер видит пространство, слот, метку, размер (кратный 64 байтам) и время прихода. Таблицы, id записей, имена полей и значения он не видит.
- AAD привязывает шифротекст к слоту и метке: сервер не может подменить метку или переставить значение в другую ячейку.

### Что остаётся видно серверу

E-mail, устройства, состав пространств, число операций и их метки времени, размеры с точностью до 64 байт, время подключений. Это задокументировано для пользователей.

## Напоминания

Планируются локально на каждом устройстве. Для веба клиент передаёт серверу расписание: время и зашифрованный текст, сервер отправляет Web Push. Детали в фазе 1.

## Проверка

- Модульные тесты и тесты на свойства (fast-check) для всего ядра.
- Детерминированная симуляция: несколько устройств, случайные операции, разрывы сети, сдвиг часов. Все устройства и сервер должны прийти к одному состоянию, равному максимуму по `hlc` для каждой ячейки.
